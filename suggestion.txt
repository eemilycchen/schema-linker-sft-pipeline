  ---
  Strengths from the raw outputs

  1. JSON format compliance — The parser handles both bare JSON (RAW[4], [9])
  and markdown-fenced (RAW[2], [5]), and the model consistently outputs one or
  the other. Almost no syntax errors on clean outputs.
  2. Table identification on simple queries — Single-table questions (RAW[2],
  [3], [5], [6]) are mostly right.
  3. Schema-valid identifiers — Both runs show tables=0, columns=0 invalid
  identifiers, meaning the model isn't hallucinating table/column names that
  don't exist in the schema.

  ---
  Weaknesses (with diagnosis)

  1. Truncated outputs (RAW[1], [18], [25], [31], [40], [49], [70], [83], [88], 
  [94], [99])

  The JSON gets cut off mid-response. This means max_new_tokens is too low at
  inference time, and possibly max_seq_length was too short during training.
  These become unparseable or partially parsed, silently dropping tables and
  columns.

  2. Empty column lists — the biggest score killer

  RAW[7], [11], [19], [20], [37], [63], [65], [78], [80] all have tables with
  []. The model identifies the right tables but gives up on columns. Your column
  score (0.24 precision, 0.28 recall) reflects this directly. The model learned
  "when uncertain, predict the table but leave columns empty."

  3. Over-prediction of tables (precision drag)

  RAW[18], [40], [42], [65], [78] dump nearly every table in the schema with
  empty columns. The model is "hedging" — it can't distinguish relevant from
  irrelevant tables so it includes everything. This tanks table precision (0.42
  → lower).

  4. Format regression in complex cases

  RAW[25] returns a list of objects inside a column list instead of a string
  array. This is a rare but catastrophic format failure — the parsed output is
  garbage.

  ---
  Plan: Data Balancing + Augmentation + Post-processing

  Concept to anchor this: Precision-Recall and the cost of false negatives

  The leaderboard metric is (P + R + F1) / 3 — it weights recall and precision
  equally. But for downstream SQL generation, missing a column (false negative) 
  is usually more harmful than including an extra one (false positive). Your
  model currently has recall < precision on columns, meaning it's being too
  conservative. The plan below is structured around increasing recall without 
  catastrophically dropping precision.

  ---
  Step 1: Post-processing (fastest win, no retraining)

  A. JSON repair for truncated outputs

  Wrap your JSON parser to handle partial output — if the JSON is cut off, try
  to close the last open brace/bracket and parse what you have. This recovers
  partial predictions from RAW[1], [18], [31], etc. instead of getting nothing.

  def repair_json(text):
      # close unclosed brackets/braces
      open_b = text.count('{') - text.count('}')
      open_sq = text.count('[') - text.count(']')
      text += ']' * open_sq + '}' * open_b
      return text

  B. Column fallback for empty lists

  When the model predicts a table with [], use BM25 / token overlap between the
  question tokens and column names from the actual schema to fill in top-k
  columns. This directly addresses weakness #2.

  question: "Show count of injuries by body region where severity is critical"
  table: INJURY (columns: AIS, REGION, CASEID, DATE, ...)
  → BM25 score: REGION=high, AIS=high (via "critical"→AIS=5 in training)
  → fill in ["AIS", "REGION"] instead of []

  C. Table count capping / pruning

  For predictions with >5 tables (all empty), apply a max-table threshold or
  require that predicted tables have at least 1 column. This removes the
  hedge-dumping pattern.

  ---
  Step 2: Data Balancing (before next fine-tune)

  Look at your train.json distribution:

  import json, collections
  data = json.load(open("train.json"))
  n_tables = [len(x["schema_links"]) for x in data]
  n_cols = [sum(len(v) for v in x["schema_links"].values()) for x in data]
  print(collections.Counter(n_tables))  # how many 1-table vs multi-table?

  The model over-predicts empty columns likely because the training data is 
  dominated by simple single-table, few-column examples, so it never learned to
  commit on complex ones.

  Balance by:
  - Oversampling examples where n_tables >= 2 or total_columns >= 4
  - Undersampling trivial single-column examples

  ---
  Step 3: Data Augmentation (adds training signal)

  A. Question paraphrasing — For each training example, generate 1-2 paraphrases
  of the question. The question wording changes but the schema links stay the
  same. This teaches the model that different phrasings map to the same schema.
  You can use a larger model (even GPT-4o-mini via API) for this.

  B. Column-name synonyms — Many columns have cryptic names (AIS, PCODE, VEHNO).
  Add augmented examples where the question uses the column's full meaning
  (e.g., "abbreviated injury scale" → AIS). This directly addresses cases where
  the model can't connect question vocabulary to column names.

  C. Hard negative mining — For examples where the model currently fails (you
  have per_question_run0-2310.csv), include those in training with the correct
  labels. The model needs more signal on the patterns it's getting wrong.

  ---
  Step 4: Increase max_new_tokens at inference

  Right now truncation is silently corrupting ~10% of outputs. Set
  max_new_tokens=512 or higher — column lists for large tables can be long.
