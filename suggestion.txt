--- POST-PROCESSING FIXES (no retraining, implement first) ---

1. Column-as-table-key recovery  [~8 outputs affected, biggest new win]
   When a predicted key does not match any real table name, check if
   it is a known column in the schema. If it is, find the table that
   owns it and add that table (with this column) to the output.
   In postprocess_output(), after `if t_lower not in table_lower2orig`,
   instead of `continue`, try:

     col_to_table = {}  # build once per db_id
     for (t_idx, cname) in schema["column_names_original"]:
         if t_idx == -1: continue
         col_to_table[cname.lower()] = schema["table_names_original"][t_idx]
     # then in the loop:
     if pred_table.lower() in col_to_table:
         parent = col_to_table[pred_table.lower()]
         rescue_cols.setdefault(parent, []).append(pred_table)

2. String-value-to-list recovery  [~5 outputs]
   When pred_cols is a string (not a list), wrap it: pred_cols = [pred_cols]
   Add this before the `if not isinstance(pred_cols, list): pred_cols = []` line.
   This recovers RAW[35], [57], [60].

3. JSON repair for truncation  [~6 outputs]
   Add to _parse_json_output() before the final `return {}`:
     # try to close unclosed brackets
     fixed = text
     fixed += ']' * max(0, fixed.count('[') - fixed.count(']'))
     fixed += '}' * max(0, fixed.count('{') - fixed.count('}'))
     m2 = re.search(r"\{.*\}", fixed, re.DOTALL)
     if m2:
         try: return json.loads(m2.group())
         except: pass

4. Schema-in-tablename extraction  [~3 outputs]
   Some outputs encode `{"TABLENAME(col1, col2, ...)": []}`.
   In postprocess_output(), before the table lookup, try:
     m = re.match(r'^([A-Za-z0-9_]+)\s*\((.+)\)$', pred_table)
     if m:
         pred_table = m.group(1)   # strip the "(col1, col2)" part
         # optionally: parse m.group(2).split(",") as fallback col candidates

5. Raise BM25 top_k  [~16 outputs with empty cols]
   Current top_k=3 is conservative. Try top_k=5 — the metric is
   (P+R+F1)/3 and recall matters as much as precision, so adding
   2 more columns has low cost if they're relevant.
   Also lower the score>0 guard to allow partial matches:
     return [col for score, col in scores[:top_k]]  # remove `if score > 0`
   (only if the question is non-empty, to avoid injecting random cols)

--- RETRAINING FIXES (needed to push past 0.45) ---

6. Switch back to lr=3e-5  [confirmed best from prior experiments]
   The current run used lr=5e-5 — previous data showed 5e-5 hurts at all
   ranks. The severe format corruption in this run (integers, sets, objects)
   is consistent with high-LR overfitting. lr=3e-5 + r=512 was 0.3319
   without BM25; with the post-processing fixes above it could reach ~0.47+.

7. Increase max_seq_length to 4096 during training
   Training at 2048 means examples with large schemas got truncated.
   The model learned to produce outputs mid-sequence, which explains
   the truncated JSON outputs at inference. Use max_seq_length=4096
   in SFTTrainer (also increase inference max_length to 4096 to match).
   Watch VRAM — may need to halve batch size or gradient_accumulation_steps.

8. Try Qwen2.5-Coder-1.5B-Instruct as base model
   Same architecture/params, but pretrained on code/SQL. Should produce
   better structured JSON output before SFT. Keep r=512, lr=3e-5 to
   isolate the model change effect.

9. Data balancing: oversample multi-table / multi-column examples
   Compute:
     n_tables = [len(x["schema_links"]) for x in train]
     n_cols   = [sum(len(v) for v in x["schema_links"].values()) for x in train]
   Oversample examples where n_tables >= 2 or total_cols >= 4.
   The column-as-table confusion pattern suggests the model never
   learned to commit on complex schemas.

10. Question paraphrasing augmentation
    Generate 1-2 paraphrases per training example using a large model.
    Same schema_links, different question wording. Teaches generalization
    across phrasings, especially for cryptic column names (AIS, PCODE, VEHNO).

  ---
  Plan: Data Balancing + Augmentation + Post-processing

  Concept to anchor this: Precision-Recall and the cost of false negatives

  The leaderboard metric is (P + R + F1) / 3 — it weights recall and precision
  equally. But for downstream SQL generation, missing a column (false negative) 
  is usually more harmful than including an extra one (false positive). Your
  model currently has recall < precision on columns, meaning it's being too
  conservative. The plan below is structured around increasing recall without 
  catastrophically dropping precision.

  ---
  Step 1: Post-processing (fastest win, no retraining)

  A. JSON repair for truncated outputs

  Wrap your JSON parser to handle partial output — if the JSON is cut off, try
  to close the last open brace/bracket and parse what you have. This recovers
  partial predictions from RAW[1], [18], [31], etc. instead of getting nothing.

  def repair_json(text):
      # close unclosed brackets/braces
      open_b = text.count('{') - text.count('}')
      open_sq = text.count('[') - text.count(']')
      text += ']' * open_sq + '}' * open_b
      return text

  B. Column fallback for empty lists

  When the model predicts a table with [], use BM25 / token overlap between the
  question tokens and column names from the actual schema to fill in top-k
  columns. This directly addresses weakness #2.

  question: "Show count of injuries by body region where severity is critical"
  table: INJURY (columns: AIS, REGION, CASEID, DATE, ...)
  → BM25 score: REGION=high, AIS=high (via "critical"→AIS=5 in training)
  → fill in ["AIS", "REGION"] instead of []

  C. Table count capping / pruning

  For predictions with >5 tables (all empty), apply a max-table threshold or
  require that predicted tables have at least 1 column. This removes the
  hedge-dumping pattern.
